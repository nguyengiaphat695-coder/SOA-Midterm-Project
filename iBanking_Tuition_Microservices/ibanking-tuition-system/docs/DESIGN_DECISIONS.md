# Phân tích thiết kế và các quyết định kiến trúc

## 1. Bám theo yêu cầu đề

Người dùng đã được cấp tài khoản đăng nhập `username/password`. Không có chức năng đăng ký. Sau khi đăng nhập, lấy họ tên, số điện thoại, email, số dư, lịch sử; người nộp được phép tra cứu và thanh toán học phí cho sinh viên khác theo MSSV; chỉ **thanh toán toàn bộ** và số dư phải đủ. Hệ thống gửi OTP qua email người nộp, OTP 6 chữ số duy nhất trong các mã đang hiệu lực, 5 phút, dùng một lần, tối đa 5 lần sai (chính sách thêm); khi thành công trừ số dư, cập nhật `PAID`, lưu lịch sử, gửi email xác nhận. Hai race quan trọng phải được chống: cùng tài khoản chi vượt số dư và nhiều tài khoản đóng một khoản học phí.

## 2. Service boundaries

| Service | Data ownership | Trách nhiệm |
|---|---|---|
| User/Account | `users`, `accounts`, `account_debits` trong `user_db` | đăng nhập JWT, xác minh sở hữu, số dư, debit idempotent |
| Tuition | `students`, `tuition_fees` trong `tuition_db` | authoritative fee amount, reservation/PAID state |
| Payment | `transactions`, `otps` trong `payment_db` | saga orchestration, OTP, lịch sử, recovery, receipt |

**Không dùng cross-DB foreign key:** tham chiếu ngoài DB được kiểm tra qua internal API. Sự thay đổi số dư chỉ do Account Service; trạng thái học phí chỉ do Tuition Service; Payment Service không tự cập nhật DB của service khác.

## 3. Luồng thành công

```text
Browser -> Gateway -> User Service: login(username,password), nhận JWT
Browser -> Gateway -> Tuition Service: GET fee theo MSSV
Browser -> Gateway -> Payment Service: POST /payments (JWT, tuitionFeeId, idempotency)
Payment -> User Service: account của chủ JWT
Payment -> Tuition Service: fee + amount authoritative, reserve(tx_id)
Payment: transaction PENDING_CONFIRM
Browser: xem summary, chấp nhận điều khoản
Browser -> Payment: /confirm
Payment -> Mailpit: gửi OTP (KHÔNG trả OTP qua API)
Browser -> Payment: /verify-otp
Payment: OTP đúng -> xử lý PROCESSING
Payment -> Tuition: start(tx_id) [reservation exclusivity]
Payment -> User: debit(tx_id, payer, amount) [SELECT FOR UPDATE + unique ledger]
Payment -> Tuition: mark-paid(tx_id) [only holder; idempotent]
Payment: SUCCESS; gửi email xác nhận; trả response
Browser: reload balance, fee status, history
```

## 4. Transaction and concurrency

**Case 1 — cùng tài khoản:** User Service locks account row `SELECT ... FOR UPDATE` and checks `balance >= amount` before DB update. DB constraint `balance >= 0` is a second line of defense. `account_debits.transaction_id` primary key ensures a repeated request for the same transaction cannot debit twice; conflicting payload with same transaction ID is rejected.

**Case 2 — hai tài khoản, cùng học phí:** Tuition Service locks the fee row `FOR UPDATE` on `/reserve`; only one transaction ID can hold the active reservation. `start` and `mark-paid` require the matching transaction ID; `PAID` cannot revert to UNPAID and has a `paid_by_transaction_id` unique reference. Payment DB has a partial unique index for successful tuition transactions.

**Distributed consistency:** A single SQL transaction cannot atomically commit both user_db and tuition_db; this is a mini Saga using an idempotent retry-forward model. After a debit, any temporarily failed `mark-paid` leaves the payment `PROCESSING`; recovery retries based on the same tx ID. It never immediately labels a network timeout `FAILED`. An unexpected conflict goes to `REVIEW` rather than blindly refunding or allowing double payment. `PROCESSING` tuition reservation intentionally does **not** auto-expire (unlike the pre-OTP `PENDING_PAYMENT` reservation). This design emphasizes money safety over temporary availability.

**Recovery limitations:** worker runs in Payment process periodically and is not a full durable distributed queue. In a production system: independent worker, message outbox, monitoring and time-bounded escalation for REVIEW cases are needed. A business reconciliation tool, refund workflow and double-entry ledger are not implemented.

## 5. Security and privacy choices

- JWT HS256 exp 1h; each public service verifies signature. User identity is determined server-side, never from payment body.
- Internal service token is a constant-time checked shared credential; the gateway never forwards `/internal/*`. It is for local demo; production should prefer service identity/mTLS, finer-grained credentials and IAM policies.
- PBKDF2-HMAC-SHA256 with random salt and 600k iterations; seed password `123456` ONLY local demo.
- 6-digit OTP generated by `secrets.randbelow`; only HMAC hashes stored (per-transaction HMAC for verification, global keyed fingerprint for active uniqueness); used flag, timestamp and retry count enforced.
- No OTP in HTTP response, frontend, API log or database plaintext; Mailpit alone stores email content for sandbox display.
- Numeric integer VND avoids floating point rounding; use `NUMERIC(18,0)` DB money storage.
- No public account debit endpoint. External `amount` or `payer_id` is rejected by model instead of trusted.
- Gateway bound to `127.0.0.1`. For Internet deployment: HTTPS, secrets rotation, per-service DB permissions, rate limit, security scanning, CSP, audit logging, tracing, fraud detection, regulatory review are required.

## 7. Out-of-scope vs production

This is a coursework simulation, not bank-grade software. No real account or payment rail, no payment gateway integration, no double-entry accounting or full real-world audit trail. Automated integration tests require actual Docker/PostgreSQL/Mailpit and must pass before claiming rubric 8–10. Demonstrate and explain these limitations instead of claiming deployed real-world reliability.
